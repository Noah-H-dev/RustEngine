=== DEVELOPER GUIDE: how to make changes / add features ===
(Extracted from source comments. Feature status/descriptions live in notes.txt.)


== THE CONTEXT SYSTEM (game_engine.rs) ==
Every screen/mode (main menu, gameplay, editor, settings, pause, ...) is a struct
that implements the GameContext trait (game_engine.rs). The trait has two methods:
    fn update(&mut self, engine, dt) -> Option<Box<dyn GameContext>>
    fn draw(&mut self, engine)
- update runs at a fixed rate (TICK_RATE); dt is seconds per tick.
- Return Some(next_context) from update to transition; None to stay.
- EditorContext exits by setting pending_exit = true, which update picks up and
  returns Some(Box::new(MainMenuContext::new())).

TO MAKE A BRAND-NEW SCREEN/CONTEXT:
  1. Create src/contexts/my_screen.rs, define pub struct MyScreenContext.
  2. impl GameContext for MyScreenContext with your update and draw.
  3. Add `mod my_screen;` (and a `pub use` if needed) in src/contexts/mod.rs.
  4. Transition into it by returning it from any other context's update.


== THE INTENT / HANDLER (APPLY) PATTERN (all egui contexts) ==
draw is split into two phases because the egui render closure borrows `engine`
(and often `self`) exclusively — you cannot call &mut self methods inside it.
  Phase 1 (inside the closure): write UI events into an Intent struct's fields.
  Phase 2 (after the closure):  hand the Intent to handler/apply methods that
                                mutate state (handle_paint, handle_spawner, apply, ...).
Snapshots of self state needed for rendering are taken into locals BEFORE the
closure to avoid borrow conflicts; editable buffers are mirrored back in the apply
phase. This pattern is used by editor.rs, settings.rs, tileset_editor.rs,
game_editor.rs. Add a new UI input by: add a field to the Intent struct, set it
inside the closure, react to it in the matching handler.


== EDITOR.RS specifics ==
ADD A NEW TAB to the right panel (RightPanelTab):
  1. Add a variant to RightPanelTab (e.g. EventPainter).
  2. In draw, add a ui.selectable_label button in the tab row.
  3. Add a `RightPanelTab::EventPainter => { ... }` arm to the match that renders
     panel content.
  4. Add any new Intent fields the panel needs and react to them in a handler.
ADD A NEW FIELD/FEATURE to EditorContext: all runtime state lives in EditorContext;
  initialise new fields in the single with_world constructor (both from_file and
  new_map call it). For FSM-style features (multi-step dialog) follow the FolderEdit
  pattern: a state enum on EditorContext, mirror its text buffer in/out of the
  Intent, apply transitions in a dedicated handler.
PERSISTING NEW DATA: map tile data saves via World::save (on intent.do_save). Unit
  templates + placements live in units.toml, written by save_units(). For a new
  type of placed object follow the same pattern: a TOML-backed file, a load_*
  helper called from with_world, and a save_* helper called whenever state changes.
KEY HELPERS: screen_to_tile_idx (egui Pos2 -> index into world.tiles, accounts for
  camera + zoom, flips y since GL y=0 is bottom / egui y=0 is top);
  build_sprite_cache (loads GLObjects keyed by palette id for drawing sprites).


== SETTINGS MENU (settings.rs) ==
ADD A NEW SETTING — two places:
  1. Add the field to Settings in game_engine.rs (e.g. `pub volume: f64`).
  2. Add one line to settings_for_tab under the right tab:
       SettingsTab::Audio => vec![ ("Volume", Number(&mut s.volume)) ],
  Settings save automatically when the user picks Return or Exit to Main Menu.
ADD A NEW TAB:
  1. Add a variant to SettingsTab.
  2. Add a selectable_label for it in the tab bar inside draw.
  3. Add a match arm in settings_for_tab (start with vec![]).
ADD A NEW WIDGET TYPE (slider, dropdown, ...):
  Extend SettingValue with the new variant and add_setting with its match arm.
Each settings_for_tab entry hands the UI a &mut directly into Settings, so edits
land in engine state with no mirror/write-back.


== TILE DEFINITIONS (tiledefs.rs) ==
A tile definition is the abstract, tileset-independent identity of a tile: id,
optional name, and shared properties (collision, folder, category). The PNG is NOT
here — that is per-tileset (the id->png "skin"). Keeping path out is deliberate: it
lets one map be re-skinned by swapping tilesets while definitions stay constant.
Source of truth on disk is gamedata/tiledefs.toml. The [[texture]] table key is kept
for back-compat with files the map editor already wrote.
ADD A NEW PROPERTY: add a #[serde(default)] field to TileDef so old files keep
loading. Render-time properties (e.g. color shift) also need the game engine to
load these. TileDefs is the central id-allocation point (create() = max id + 1).


== TILESETS / SKINS (tileset.rs) ==
A tileset is the per-skin mapping from abstract tile id -> PNG filename in assets/.
On-disk format is the same plain `id filename` text (one per line, '#' comments) the
legacy id.txt / game engine's load_textures already use, so existing tilesets and
the game loader keep working. Convention: tilesets live in tilesets/*.txt so the
editor can scan and list them. New tilesets start as a copy of the currently-selected
one (cheap variants: "forest_dark" from "forest"). Tileset::ensure_default() creates
tilesets/Default.txt (migrating a legacy root id.txt if present) and is idempotent —
safe to call every startup.


== GAME-DATA EDITOR (game_editor.rs) ==
Definition (Creature tab here) and placement (map editor Spawner tab) both
round-trip the whole UnitRecord, so editing stats here preserves a template's placed
positions and vice-versa. The two never run at once (separate contexts). The Creature
tab owns create/edit/delete of templates and the "+ Add PNG" flow that mints a
Creatures-category tile def; the Spawner tab only places them.


== TILESET EDITOR (tileset_editor.rs) ==
Two tabs: Definitions (abstract tile namespace -> tiledefs.toml) and Tileset
(per-skin PNG assignment -> tilesets/ files). Active tileset path persists in
Settings.active_tileset so selection survives restarts. Only one inline text input
(InlineEdit FSM) is ever open at a time — naming a tile, a folder, or a new tileset
all go through it.


== SAVE GAME / DIVISION OF TRUTH (game_engine.rs, entity.rs) ==
game.toml = which map + tileset + live unit state (position + patrol_idx), matched to
templates by load order. player.toml `spawn` = the player's position (doubles as the
saved location). Together they let "Continue" resume a session. A fresh "Run" starts
at the map's ---SPAWN--- marker and ignores player.toml `spawn`.
- save_player_spawn preserves the rest of player.toml (sprite_id, stats, extra
  [[unit]] entries); if the file exists but won't parse it bails rather than
  overwrite and lose data.
- units.toml stays the template; game.toml `units` are live overrides on top.


== MAP FILE FORMAT (game_engine.rs World) ==
Space-separated tile-id grid, then MAP_PHYSICS_DELIMITER, then a parallel 0/1 solid
grid. Row 0 in the world = bottom row of the file (both grids are reversed on save).
---SPAWN--- section (MAP_SPAWN_DELIMITER) is only emitted when a spawn is set, so maps
that never used it stay byte-identical.


== INPUT: NEUTRAL KEYS (lib.rs tools::Key, game.rs) ==
The SDL event pump translates raw scancodes into an engine-neutral Key enum and
pushes the frame's presses into Engine.keys_pressed. Each context interprets them:
GameRunningContext maps WASD -> actions (keys_to_action) and Escape -> settings.
GOTCHA: keys_pressed and player_action are cleared in the run loop AFTER each tick,
so input detection must live in update(), NOT draw() (draw runs after the clear).
To surface a new key: add an arm to Key::from_scancode in lib.rs — no context or pump
change needed. Discrete-press only today (held-key state deferred).


== PLAYER / UNIT ACTION CHANNEL (game_engine.rs, entity.rs, game.rs) ==
The player's per-tick intent lives on the Engine as player_action (read from input,
reset each tick). Each non-player Unit owns its own current_action (source of truth),
set by Unit::decide (AI hook) and applied by Unit::apply_action. game.rs::step_units
runs decide -> execute -> patrol; the execute phase builds a sparse (unit_index,
action) work-list, ready for initiative/turn-order later.
Two "action" types not to confuse: item::Actions (per-item metadata, item.rs) vs
tools::actions enum (NONE | MOVE{dir}, what actually executes).

HOWTO — make a collected KEY drive a player action (4 seams):
  1. Pickup: load items into engine.items (today it's vec![]//update this) and in
     game.rs update, when player.position == item.position && item.class==KEY, set
     carried & push to player.inventory.
  2. Add an actions variant (e.g. USE/UNLOCK) in lib.rs; update every match on actions.
  3. In keys_to_action/update: if the use-key is pressed AND inventory has a KEY item,
     set player_action = actions::USE{..} instead of a move.
  4. Execute: `if let actions::USE.. = player_action` block applies the effect (unlock
     adjacent tile, consume key). To let the item declare its own behavior, read
     item.action_list instead of hard-coding KEY.
Missing today: runtime pickup + a non-MOVE variant in the actions enum.


== SERDE COMPAT GOTCHA (stats.rs and any persisted record) ==
Container-level #[serde(default)] fills any field missing from a TOML file from the
Default impl. Without it, adding a new field silently breaks every older
units.toml / player.toml that predates it: the whole file fails to parse and the
loader falls back to empty. Always add new persisted fields as #[serde(default)].


== UI FONT (gui/mod.rs) ==
The engine-wide typeface is the IBM VGA 9x16 (CP437) font, embedded via include_bytes!
and set as default for both proportional and monospace families. Changing that
include_bytes! path restyles all UI text at once.


== MISC GOTCHAS ==
- GLObject has no Drop impl: replacing a Tile's sprite drops the old GLObject but does
  NOT free its GPU resources. Add a Drop impl to GLObject to fix.
- resolve_map_path (menus.rs): user-entered map paths resolve under MAPS_DIR ("maps");
  absolute paths or paths already rooted in maps/ pass through verbatim.
